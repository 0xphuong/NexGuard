# Migration runbook — v2.2.0 (L7-A Phase 1)

> **Scope**: six additive migrations that land the data foundation for
> the L7 ZTNA admin UI. No code path in `2.2.0` references any of the
> new tables at runtime until an admin explicitly creates rows, so
> applying these migrations on a live production is **non-disruptive**
> and reversible. Read alongside `docs/decisions.md` ADR-007 → ADR-014
> for the design context.

## Summary

| # | Migration | Object | Type |
|---|---|---|---|
| 1 | `20260620000001` | `access_groups` | NEW table |
| 2 | `20260620000002` | `user_group_memberships` | NEW table (composite PK) |
| 3 | `20260620000003` | `applications` | NEW table |
| 4 | `20260620000004` | `application_allowed_groups` | NEW table (composite PK) |
| 5 | `20260620000005` | `users` | add column `access_scope` |
| 6 | `20260620000006` | `org_settings` | NEW table + seed row |

All operations are **`ALTER ADD`** or `CREATE` — no column drops, no
data backfills, no rewrites. Postgres applies the `NOT NULL` +
`DEFAULT 'limited'` add on `users.access_scope` as a metadata-only
operation (fast default) on PG ≥ 11, so there's no full-table scan.

## Pre-flight

1. **Confirm Cloak vault is configured** (`config :fz_http, FzHttp.Vault, ...`).
   The new `applications.key_pem` column uses `FzHttp.Encrypted.Binary`.
   No row gets written in 2.2.0 until an admin uses the "Upload" cert
   source in the UI, so a missing vault is not an immediate blocker —
   but worth verifying ahead of time:

   ```bash
   docker compose -f docker-compose.prod.yml exec nexguard \
     /app/bin/nexguard rpc 'IO.inspect(Application.get_env(:fz_http, FzHttp.Vault))'
   ```

2. **Take a database backup** (always — even though these migrations
   are reversible):

   ```bash
   docker compose -f docker-compose.prod.yml exec db \
     pg_dump -U postgres -d nexguard_dev \
     > ~/nexguard-pre-v2.2.0-$(date +%Y%m%d-%H%M%S).sql
   ```

3. **Confirm kernel ≥ 5.6.9** (already required for current port-based
   rules — unchanged; called out only because L7-C will add new
   nftables chains in a later release).

## Apply

Migrations are auto-run on the next container start, per
`docker-compose.prod.yml`:

```bash
cd /path/to/nexguard-prod
git pull origin main
docker compose -f docker-compose.prod.yml up -d --build
```

Watch the boot log for the 6 migration messages:

```bash
docker compose -f docker-compose.prod.yml logs --tail=200 nexguard \
  | grep -i "migrat"
```

You should see lines for each of:

```
== Running 20260620000001 FzHttp.Repo.Migrations.CreateAccessGroups.change/0 forward
== Running 20260620000002 FzHttp.Repo.Migrations.CreateUserGroupMemberships.change/0 forward
== Running 20260620000003 FzHttp.Repo.Migrations.CreateApplications.change/0 forward
== Running 20260620000004 FzHttp.Repo.Migrations.CreateApplicationAllowedGroups.change/0 forward
== Running 20260620000005 FzHttp.Repo.Migrations.AddAccessScopeToUsers.change/0 forward
== Running 20260620000006 FzHttp.Repo.Migrations.CreateOrgSettings.change/0 forward
```

## Verify

A paste-and-run verification script is shipped at
`apps/fz_http/priv/repo/verify_l7a_schema.sql`. It checks migration
versions, table presence, the composite PKs, the singleton CHECK on
`org_settings`, the unique constraints on `applications.hostname` +
`applications.virtual_ip`, and runs a transactional smoke test of the
cascade-delete chain.

```bash
docker compose -f docker-compose.prod.yml exec -T db \
  psql -U postgres -d nexguard_dev \
  < apps/fz_http/priv/repo/verify_l7a_schema.sql
```

Every section should print `PASS` (or `PASS: ...` from the NOTICE
blocks). A `FAIL` line means something didn't apply cleanly — stop
the deploy and capture the script output before rolling back.

## Quick smoke (read-only, after deploy)

```bash
docker compose -f docker-compose.prod.yml exec nexguard \
  /app/bin/nexguard remote
```

```elixir
# Singleton row is present
FzHttp.OrgSettings.get()
#=> %FzHttp.OrgSettings.Settings{id: 1, l7_enabled: false, ...}

# Every existing user got the default access_scope
FzHttp.Repo.all(FzHttp.Users.User)
|> Enum.map(& &1.access_scope)
|> Enum.frequencies()
#=> %{limited: <count>}

# VIP allocator works inside a rolled-back transaction (doesn't persist)
FzHttp.Repo.transaction(fn ->
  IO.inspect(FzHttp.L7.VipAllocator.allocate_inside_transaction(),
             label: "first free VIP")
  FzHttp.Repo.rollback(:smoke)
end)
#=> %Postgrex.INET{address: {10, 99, 0, 1}, netmask: 32}
```

## Rollback

If verification fails, reverse with `mix ecto.rollback`:

```bash
# Reverse the six new migrations
docker compose -f docker-compose.prod.yml exec nexguard \
  /app/bin/nexguard eval 'FzHttp.Release.rollback(FzHttp.Repo, 20260619999999)'
```

Or, more granularly via the dev container with `mix`:

```bash
docker compose exec app mix ecto.rollback --step 6
```

After rollback:

- The five new tables are gone.
- `users.access_scope` column is removed.
- The seed row in `org_settings` was DELETEd by the `change/0`
  rollback branch.
- The app container does not crash because `2.2.0` modules merely
  reference these tables on demand — nothing reads them at boot.

If something is still wrong, restore from the pg_dump backup taken in
**Pre-flight step 2**.

## Operational impact

- **End users**: no visible change. The L7 enforcement subsystem is
  dormant (`l7_enabled = false` by default, no proxy / CoreDNS /
  step-ca daemons deployed in this release).
- **Admins**: four new admin surfaces show up in the sidebar
  immediately on first login after deploy — Access Groups,
  Applications, and L7 Enforcement under Settings. Existing admins
  must **sign out + back in** to pick up the new permissions
  (subjects cache their permission set at sign-in; see
  commit `e767a8b`).
- **Data**: the new tables stay empty unless an admin uses them.
  Total row count delta on first day is normally 0–100 rows.
