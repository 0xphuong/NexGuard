# Migration runbook — v2.3.0 (L7-B Phases 1–5)

> **Scope**: one additive migration that lands the JWT signing-key
> table, plus a small set of new HTTP endpoints / GenServers that
> the upcoming L7 proxy daemon (L7-D) will consume. No existing
> route, table, or code path changes behaviour — the L7 subsystem
> stays dormant until the proxy daemon ships. Applying this on a
> live production is **non-disruptive and reversible**.

## Summary

| # | Migration | Object | Type |
|---|---|---|---|
| 1 | `20260621000001` | `l7_signing_keys` | NEW table |

The new table is empty after the migration. `FzHttp.L7.JwtSigner`
inserts the first active row the first time it boots — there is
**no manual bootstrap step** (no `mix nexguard.l7.bootstrap_keys`
task is required, despite the wording in the original L7-B tracker).

## Pre-flight

1. **Confirm Cloak vault is configured.** `l7_signing_keys.private_pem`
   uses `FzHttp.Encrypted.Binary`, the same encrypted-at-rest type
   that already gates `applications.key_pem` since v2.2.0 and
   `devices.preshared_key` since v1.x. If the vault is misconfigured
   the `JwtSigner` GenServer crashes on first bootstrap (visible in
   container logs as `[FzHttp.L7.JwtSigner] crash ...`) without
   touching the rest of the app.

   ```bash
   docker compose -f docker-compose.prod.yml exec nexguard \
     /app/bin/nexguard rpc 'IO.inspect(Application.get_env(:fz_http, FzHttp.Vault))'
   ```

2. **Take a database backup** (always):

   ```bash
   docker compose -f docker-compose.prod.yml exec db \
     pg_dump -U postgres -d nexguard_dev \
     > ~/nexguard-pre-v2.3.0-$(date +%Y%m%d-%H%M%S).sql
   ```

## Apply

Migration is auto-run on the next container start per
`docker-compose.prod.yml`:

```bash
cd /path/to/nexguard-prod
git pull origin main
docker compose -f docker-compose.prod.yml up -d --build
```

Watch the boot log for the migration line:

```bash
docker compose -f docker-compose.prod.yml logs --tail=200 nexguard \
  | grep -iE "migrat|l7_signing|jwt|bundle_builder"
```

You should see:

```
== Running 20260621000001 FzHttp.Repo.Migrations.CreateL7SigningKeys.change/0 forward
```

Followed by the GenServer boot messages (`JwtSigner`, then
`BundleBuilder` once `JwtSigner` is ready).

## Post-flight

Verify the four new endpoints + the bootstrap audit row.

### 1. JWKS endpoint (public)

```bash
curl -s https://<your-portal>/.well-known/jwks.json | jq
```

Expect a `{"keys":[{...}]}` array with one entry (the active key
just bootstrapped):

```json
{
  "keys": [
    {
      "alg": "RS256",
      "e":   "AQAB",
      "kid": "<uuid>",
      "kty": "RSA",
      "n":   "<base64url modulus>",
      "use": "sig"
    }
  ]
}
```

`curl -sI` should show `cache-control: public, max-age=300`.

### 2. Identity endpoint

Pick any active VPN device IP (e.g. `100.64.0.5`):

```bash
curl -s https://<your-portal>/internal/sessions/by_vpn_ip/100.64.0.5 | jq
```

Expect the identity payload (see `NEXGUARD_LOGIC.md` §17 for the
shape). Unknown / unparseable IPs return:

```json
{ "error": "unknown_vpn_ip" }
```

### 3. Bundle endpoint

```bash
curl -sD - https://<your-portal>/internal/bundle.json | head -25
```

Expect headers including `etag: "v1"` and
`x-nexguard-bundle-signature: eyJ...`. Body is the JSON bundle (see
§17 bundle schema).

### 4. Audit row for the bootstrap

```bash
docker compose -f docker-compose.prod.yml exec db \
  psql -U postgres -d nexguard_dev -c \
  "SELECT action, target_id, metadata, inserted_at \
   FROM audit_logs WHERE action LIKE 'l7.signing_key%' \
   ORDER BY inserted_at DESC LIMIT 5;"
```

Expect one row with `action = 'l7.signing_key.bootstrap'`,
`target_id = <kid>`, `metadata = {algorithm: "RS256", bits: 2048}`.

> Note: if the production container booted from an earlier release
> that lacked the `l7.signing_key.*` whitelist (`AuditLog.changeset`
> `validate_inclusion`), the very first bootstrap audit row was
> silently dropped. The fix landed in commit `366b084`; subsequent
> rotations (or a re-bootstrap on a fresh DB) audit correctly. We
> intentionally do **not** backfill the missed row because
> `l7_signing_keys` itself already carries `kid + inserted_at`, so
> forensic provenance is intact.

## Operational notes

- **Bundle dependency on JwtSigner**. The supervision tree starts
  `JwtSigner` before `BundleBuilder`; if `JwtSigner` fails to boot
  (Cloak misconfigured, DB down), `BundleBuilder.init/1` queues a
  compile but the compile call to `JwtSigner.jwks/0` will block. The
  `:one_for_one` strategy will restart both up to the default crash
  threshold; if you see repeated restarts, fix `JwtSigner` first.

- **`/internal/*` exposure**. Both `/internal/sessions/by_vpn_ip/:ip`
  and `/internal/bundle.json` are mounted under the placeholder
  `:api_internal` pipeline. Phase 1 of L7-B intentionally leaves
  them unauthenticated; the mTLS plug + cert provisioning ship in
  the L7-D release alongside the proxy daemon that actually calls
  these endpoints. Until then, treat the endpoints as **internal by
  network convention**, not by authentication.

- **No key rotation in this release**. `JwtSigner.rotate/3` exists
  in the API but is not surfaced in the admin UI; key rotation is a
  manual `iex` call for now. The audit + grace-window plumbing is
  ready for the rotation button when it lands.

## Rollback

Single migration; reversible:

```bash
docker compose -f docker-compose.prod.yml exec nexguard \
  /app/bin/nexguard eval "Ecto.Migrator.run(FzHttp.Repo, :down, all: false, step: 1)"
```

The `l7_signing_keys` row(s) get deleted with the table. Re-running
forward re-creates the table and `JwtSigner` re-bootstraps a fresh
key on the next container start. Any JWTs minted with the dropped
key obviously no longer verify — irrelevant in v2.3.0 because no
consumer is calling the endpoints yet.
